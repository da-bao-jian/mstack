# W8a — browser bridge signer

Completed on 2026-10-11 (Asia/Taipei), from `125738c` on `main`. This report covers W8a only. Fable's assignment replaces the plan's persistent-daemon/token-file wording with an in-process, one-shot bridge. WalletConnect (W8b) and W9 are not part of this delivery.

## What was built

- `packages/signers/src/browser.ts`: one Proposal per HTTP server, bound to `127.0.0.1` on a random port. It prints its URL through the CLI, opens the browser, and closes after one accepted signature, human rejection, expiry, or cancellation.
- `packages/signers/src/browser.html`: one HTML page imported with Bun's text loader and bundled into the binary. It discovers EIP-6963 providers, falls back to `window.ethereum`, requests accounts, and displays the purpose, expected owner, selected account, exact text or typed-data JSON, digest, and expiry countdown.
- `packages/signers/src/interactive.ts`: a copied public signing view, digest validation, exact-payload checks, pinned-chain validation, and viem signature recovery. The view excludes the Proposal's submission body and other stored state.
- `packages/signers/src/open-url.ts`: injectable system-browser launch using `open`, `xdg-open`, or Windows `start`, with arguments passed as an array.
- `packages/signers/src/index.ts`: exports the browser backend and adds optional `chainId(): Promise<number>`. The browser returns the wallet's chain reported by the page.
- `apps/cli/src/p1.ts` and `run.ts`: `signer=browser` and `--with browser`, updated help, injected `openUrl`, policy/owner rechecks around the wallet wait, and cleanup in `finally`. Browser signing needs no secret or TTY.
- `packages/proposals/src/store.ts`: passes a copy of the stored Proposal into the signer connection callback. The stored-body submission, expiry checks, recovery, and permanent used marker remain in force.
- `packages/signers/test/{browser,browser-page}.test.ts`, `fake-browser-wallet.ts`, and `loopback.ts`: real loopback HTTP tests plus execution of the bundled page script in a VM with a scripted provider.
- `apps/cli/test/browser.test.ts`, `test/fixtures/browser-flow.ts`, and `scripts/smoke-browser.ts`: full fake-server Proposal flow, covering both config selection and the command-line override. Root and CLI manifests expose `smoke:browser`; the root test bridge includes the CLI tests.
- Root, CLI, and signer READMEs describe the available backends and browser flow. The custody statement is unchanged.

No dependencies were added. The existing pinned viem provides message and typed-data recovery; Bun provides the loopback HTTP server and text import. The lockfile is unchanged.

The resumed TypeScript failure was in the browser-page test: its text assertion preceded the guard that excludes an undefined fixture message. Moving the guard before the assertion preserves the runtime check and satisfies strict typing.

## Security checks and lifecycle

Each run creates a random 32-byte token and a separate CSP nonce in memory. Neither is written to disk. Every request requires the correct token and Host; every POST also requires the exact bridge Origin and JSON content type. Token comparison uses a fixed-format check and constant-time comparison. Request bodies are capped at 4096 bytes.

The assigned endpoints are `GET /sign/<id>?t=`, `GET /api/proposal?t=`, and `POST /api/signature?t=`. Two supporting POST endpoints use the same token and Origin checks: `/api/account` reports the connected account and chain, and `/api/reject` ends the interaction on human cancellation.

The account handshake resolves `address()` before signing. The page stays disabled until the CLI invokes the signing method, after its permanent `.signature-used` marker is written. The integration fixture checks that marker before its fake wallet signs. A second signing invocation or accepted POST cannot reuse the bridge.

The server checks the submitted address against the stored owner and independently recovers the signature using viem `recoverMessageAddress` or `recoverTypedDataAddress`. It checks expiry before and after recovery and checks a pinned chain against the page's reported chain. Wrong tokens, Origins, accounts, signatures, or chains receive a short 4xx response and leave the bridge waiting. Human rejection and expiry end the interaction.

The page places wallet names and Proposal content through `textContent`. A mismatched account appears in red and disables signing. Text uses hex-encoded UTF-8 with `personal_sign([messageHex, address])`; typed data uses `eth_signTypedData_v4([address, JSON.stringify(typedData)])`. A pinned domain chain is selected through `wallet_switchEthereumChain` before signing. A refused switch is shown; the page never calls `wallet_addEthereumChain`.

The response CSP is:

```text
default-src 'none'; script-src 'nonce-<random>'; style-src 'nonce-<random>'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

The page loads no external resources. Responses also set `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and `X-Frame-Options: DENY`. Tests check that the served HTML contains no HTTP(S) references and that the CSP nonce matches the script and style.

## Bun keep-alive shutdown edge case

On Bun 1.3.8, calling `server.stop(false)` from inside a fetch handler left keep-alive sockets able to serve another request. A minimal local reproduction and the bridge's shutdown tests exposed this behavior.

The bridge marks itself terminal immediately, so concurrent or repeated submissions receive 409. For an accepted signature or explicit rejection, it allows a 10 ms flush window for the final HTTP response, then calls `server.stop(true)` to close all sockets. The signing promise resolves only after that close completes. Expiry and cancellation close immediately. All responses also request `Connection: close`.

Tests verify exactly one accepted POST, refusal of another signing call, and that a subsequent connection fails after completion, rejection, or expiry. No persistent daemon remains.

## W8b — WalletConnect

Completed on 2026-10-11 (UTC) on `wip/w8b`, rebased onto `main` at `8dd7aa9`. This section replaces the blocked draft. The W8a report above remains its historical delivery record. ### What was built

- `packages/signers/src/walletconnect.ts`: one WalletConnect session and one signing request for each immutable Proposal. Text uses `personal_sign([hexUtf8Message, owner])`; typed data uses `eth_signTypedData_v4([owner, JSON.stringify(storedTypedData)])`. The required namespace grants only that method and chain. Account, method, chain, session expiry, exact payload and recovered owner are checked before acceptance. Session updates/events/deletion/expiry cancel the interaction. All waits share the Proposal deadline, and late approvals or signatures cannot revive it. There is no application retry.
- `walletconnect-client.ts`, `walletconnect-sdk.ts`, and `walletconnect-worker.ts`: the typed SDK adapter and a short-lived worker with fresh memory storage and a random storage namespace. SDK telemetry is disabled and the logger is silent. Protocol keys, sessions and pairings are never written to disk. Cleanup attempts session/pairing disconnects, stops the heartbeat, closes the relay, and terminates the worker within a one-second cleanup budget.
- `walletconnect-qr.ts`: terminal QR rendering, plus the pairing URI in plain text. `chainId()` reports the authorized session namespace. A domain chain pins typed-data requests; otherwise the transport uses `eip155:1` without adding a chain to the signed message.
- CLI config, help and `p1.ts`: public `walletconnect_project_id` with no default, validated as 32 hexadecimal characters, and `signer=walletconnect` / `--with walletconnect`. Missing configuration fails before SDK initialization. Locked policy, owner changes, the permanent used marker, three Proposal expiry checks, recovery and stored-body submission remain in force. Main's legal/venue submit plans and stale-terms handling were preserved.
- Current staging preflight recognizes WalletConnect only with its project ID. HL binding with this backend pins `hl_signature_chain_id` (default `0xa4b1`, Arbitrum), because WalletConnect authorizes a chain namespace rather than reporting an independent current wallet chain. It does not fall through to the browser connection step. Tests stage and submit the HL approval through the fake venue. Browser and keystore behavior stays as approved in W9.
- Mock signer/client/worker and CLI tests, `scripts/smoke-walletconnect-mock.ts`, and the guarded live smoke. The root test bridge and both package manifests include the new commands. The worker is bundled in the library and CLI builds; knip lists it and the compiled test probe as entrypoints.
- Root, CLI and signer READMEs explain project IDs, relay use, backend selection and cleanup. The preamble now reports `SIGNER: walletconnect`; all nine skills were regenerated for both hosts. The existing consent rules, setup menu, custody statement, MCP tools, Proposal model, and browser bridge were preserved. No new signing tool or setup flow was added.

### Installed SDK validation and integration fixes

The adapter was checked against the installed **2.25.0** declarations: `sign-client/dist/types/{index,client}.d.ts`, `types/dist/types/sign-client/{client,engine,session}.d.ts`, and `types/dist/types/core/{core,relayer,pairing}.d.ts`. Its init storage/options, `connect` result and `approval()`, `request`, `session.get`, `on/off`, `disconnect`, pairing disconnect, heartbeat stop and `transportClose()` all typecheck without production casts to the SDK type. Tests mock `SignClient.init` and verify argument forwarding, events, storage options and cleanup against the installed module.

Two runtime details needed fixes:

1. Bun 1.3.8's dynamic import exposes the package's CommonJS wrapper as `default`, not the constructor. The draft's default import would fail at runtime despite passing TypeScript. The adapter now imports the named `SignClient` export; the real installed export is used in the adapter tests.
2. SDK `transportClose()` stops relay reconnect scheduling, but its engine's `createDelayedPromise` retains approval/request timers. An SDK initialization can also complete after the caller's deadline. The worker gives these resources a bounded lifetime without calling private engine methods or altering installed sources. Graceful disconnects get up to 500 ms; the parent terminates the worker after cleanup or at one second. Tests retain timers deliberately, stall initialization/approval/request/close, and verify termination and late-result refusal. Worker termination also discards the SDK's per-prefix global Core cache.

The CLI lists both main and worker entrypoints, as required by [Bun's standalone worker build](https://bun.sh/docs/bundler/executables#worker). On the installed Bun version the embedded worker resolves with a `.js` name; explicit entry naming keeps it next to the executable's virtual entrypoint. An offline test compiles the real bridge and worker with a mocked SDK, launches it from a temporary directory, recovers the exact signature and confirms prompt process exit despite a retained worker timer.
