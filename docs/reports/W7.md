## Signing and storage rules

The staged Proposal stores the endpoint, route, full unsigned body, signature field, message or typed data, and preflight plan. The body is copied from that stored record at submission, with only the signature added. Config changes do not redirect a staged submission. Nonces and prices are never refreshed at sign time.

`stageOpenBody` uses `crypto.randomUUID()`, unix seconds, the marks supplied at staging, and a zero default minimum APY. Optional fields are absent unless set. It rejects unverified leverage and margin settings. The ported builder still preserves all upstream optional segments for later verified callers.

Proposal files, counter files, intent hashes, signature markers, and keystores use 0600 permissions. Proposal writes use temporary files, fsync, and atomic rename. A separate intent hash detects edits to stored signing or submission fields. Timestamps use milliseconds in the Proposal and seconds in the server body. Expiry remains 300 seconds after the staged request timestamp, including when storage crosses a second boundary.

Preview runs the persisted plan again, records `previewed`, then `awaiting-signature`, and stops. Failed checks become `rejected`. Sign refuses locked policy, missing preview, terminal state, expiry, owner mismatch, or signer mismatch. CLI policy and owner are checked again after the TTY unlock. The displayed message and digest come from the same persisted payload passed to the signer.

An exclusive, synced `.signature-used` marker is written before invoking the signer. It is never removed. A second process, restored Proposal JSON, crash, signer failure, or failed submission cannot obtain another signing attempt. Signature recovery is checked against the stored owner before submission. Expiry is checked before unlocking/signing, after signing, and before sending. The submission deadline also covers rate-limit waiting. An expired result is never submitted.

The server answer is stored. HTTP readiness errors retain their full response body. A transport failure is treated as ambiguous and never retried. Successful submission remains `submitted`: it does not claim that a task is running. The `confirmed` model state is reserved for later verified execution evidence.

## Dependency and keystore format

Added **viem 2.57.4**, pinned in the three new packages and CLI. It provides local account creation, EIP-191/EIP-712 hashing/signing, address validation, and signature recovery. The fake server uses the same recovery primitives as the real server. No wallet SDK, browser bridge, session signer, or custom secp256k1 implementation was added. See [viem local accounts](https://viem.sh/docs/accounts/local/privateKeyToAccount).

The encrypted payload uses the reference's base64 `iv`, `authTag`, and `ciphertext` fields. The vendored `kek.ts` contains interfaces only, so the local passphrase envelope is new: random 32-byte salt, scrypt N=32768/r=8/p=1, AES-256-GCM with a random 12-byte IV and 16-byte tag. Version and address are authenticated as additional data. Files cannot be overwritten; symlinks and broad file permissions are refused.

No passphrase or key is printed. Decrypted buffers are cleared. JavaScript strings and viem account state cannot be guaranteed to erase immediately; this is a local keystore, not a hardware key boundary.

## Open questions and deliberate limits

1. W7 says every route in PRD §5.2, but that table includes P3 complex-order create/cancel routes. The vendored server index names them; the route implementation, request types, and message fixtures are absent. A clarification was requested. This delivery implements arbitrage and binding and leaves complex orders unimplemented rather than inventing a request schema. Fable should confirm the P3 deferral or supply the missing reference.
2. The rate limiter shares one 500 ms schedule per host across client instances in a process. Separate CLI processes do not share a filesystem rate budget.
3. Keystore encryption follows the supplied blob shape, but the reference includes no local scrypt implementation to port byte-for-byte. The new envelope is documented above.
4. A crashed operation can leave a lock directory. The client fails closed and provides no automatic stale-lock removal. A used signature marker is permanent. Intent hashes detect drift but do not defend against an attacker who can rewrite every file in the user's account.

No generic mutation staging CLI, live position, venue leverage change, browser/WalletConnect signer, binding ceremony, legal flow, new skill, or MCP signing tool was added. Those belong to W8–W11. The current skills remain conservative and read-only. Versions stay at 0.1.0 until W11.

The PRD and reference tree are unchanged. No remote was changed and no push was made.
