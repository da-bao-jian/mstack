# W27 — streamlined signing and onboarding

Built on `main` after 0.4.1 and W26. No runtime dependency was added. The version was not changed; the notes sit under Unreleased.

## Scope

Make signing and onboarding fast and keep the human in one place, without moving the
security boundary: the agent never holds a signing key, every mutation is staged with exact
bytes and a preview, the exact id rule holds, the hook fails closed, and single-use markers
stay. The signing UX audit (session notes) measured the old flow at five human inputs plus
two wallet clicks and at least two agent turns after staging against a five-minute clock
that started at staging.

## Delivered

- **Onboarding in one wallet session.** `mob onboard --native` stages one ceremony `c-N`
  whose steps are: accept the legal terms when they are not accepted, prepare, one wallet
  request per venue, the binding read, and a key-creation step added after the venues bind.
  `mob sign c-N` walks every step in one browser, WalletConnect, or keystore session, posts
  the legal acceptance to the auth server, creates the scoped key, stores it through the
  configured key store, and prints `Ready · N venues bound · key mobius_… · cap $…`. The
  secret never prints. Flags `--name` and `--max-size` set the key (defaults `mstack`,
  `$5,000`). Previously the same path needed three authorizations and three browser visits,
  and the documented default sent the user to the Mobius page to paste the key into the chat.
- **The clock no longer starts before the human reads.** API-submit Proposals keep a
  15-minute window (they carry no signature; wallet Proposals keep the server's 300 seconds).
  `mob restage <id>` stages an expired task Proposal's intent again under a new id with a
  fresh preflight and stops; `mob sign` and `mob submit` on an expired id do the same. The
  staging command is recorded next to the Proposal (`<id>.request.json`, mode 0600) so the
  intent is the user's own words, not a copy of stale bytes.
- **One click to authorize.** The Bash sign guard accepts the answer the human chose from an
  AskUserQuestion the assistant asked, when the chosen label starts with `Submit p-N` or
  `Sign p-N` (or `Sign c-N`) and the verb matches the command. Question text, other tool
  results, a keystore choice, and a later typed message never grant consent. The open, close,
  manage, setup, and bind skills now offer those labels in the same reply as the staged card.
- **Fewer turns.** The open skill stages at once when the user's words give both legs and the
  size, and asks only for what is missing. The first-open risk questions are due once per
  owner per day: `mob risk-ack` records them and `mob hello --json` reports
  `riskInterview.due`.
- **Session deadline.** A ceremony's wallet session now outlives the server's binding window by
  15 minutes so status polling and the key step complete; each step still enforces its own
  expiry and the browser signer refuses any step past the session deadline.

## What did not change

The agent never runs keystore signing; the human runs `mob sign <id> --with keystore` in their
own terminal. `mob submit` under manual policy still needs the exact id, because the key path
has no other human gate. The hook stays fail-closed with the 30-second timeout. Signature and
submission markers stay single use. A persistent local approver for keystore users and the
PRD 6.6 session grants remain the next steps; both were designed in the audit and are not
built here.
