# W20 — onboarding ceremony

## Delivered

- Added `mob onboard` with owner prompting, `app_base` configuration, the
  one-hour per-owner opener stamp, public-read checklist, TTY watch mode, and
  the agent-safe one-shot path.
- Added `mob onboard --native` and `mob bind --all`. Both stage one durable
  `c-N` ceremony and use the W18 native batch API.
- Added ceremony storage under `ceremonies/c-N.json` with Proposal-equivalent
  permissions, locking, integrity checks, exact signing bytes, signatures,
  idempotency keys, and the latest batch read.
- Added ceremony signing for keystore, WalletConnect, and browser signers. A
  keystore ceremony unlocks once. WalletConnect pairs once. The browser uses
  one tab and requires a separate click for every displayed request.
- Kept `mob sign p-N` and the single-Proposal browser page unchanged. The old
  `mob bind <venue>` path also remains available for repair.
- Made Lighter `accountIndex` optional in `BindingTarget`. The native path only
  sends it after an explicit `--lighter-account N`; otherwise the server owns
  discovery and its error text reaches the user.
- Added `smoke:onboard` and `smoke:ceremony`. No external runtime dependency
  was added.

## Browser onboarding checklist

The page URL is always printed as:

```text
Open https://app.mob.exchange/?nav=api
```

The opener receives no owner, receiver, or other query data. `MOB_NO_OPEN` and
`BROWSER` are honored. A private stamp limits opening to once per hour for each
owner, while reruns still print and refresh the checklist.

The checklist can show every required state:

```text
Legal  ✓ accepted
Legal  ✗ missing

hl      ✓ bound
hl      ✗ needs repair · key_invalid
hl      – not bound · not_bound

Key    – none
Key    ✗ stored mobius_ab12… · rejected
Key    ✓ verified ok · mobius_ab12…
```

The real readiness issue replaces `key_invalid` or `not_bound`. A stored key is
verified with `GET /v1/delta-neutral/tasks?limit=1` through
`@mstack/mobius-api`. The key itself is never printed.

These two sentences appear verbatim below the checklist:

```text
Then the user copies the key and pastes it into the chat; the agent stores it with `mob keys import --stdin` and the CLI never prints it again.
A human at a terminal may instead run `mob keys import` and paste it hidden.
```

On a TTY, watch mode redraws every five seconds until ready or the 15-minute
budget ends. It is the default on a TTY and can be requested with `--watch`.
An agent shell prints once and exits zero. Its final line is one of:

```text
Next: bind hl on the page
Next: paste the key in the chat
Next: mob keys import --stdin
Ready
```

When complete, onboarding prints the normal home screen and this summary:

```text
Ready · 2 venues bound · key mobius_ab12… · cap $5,000
Ready
```

## Ceremony state machine

```text
awaiting-prepare-signature
  -> preparing
  -> awaiting-request-signatures
  -> submitting
  -> polling
  -> complete | partial | failed

Any unsigned user rejection -> partial
Expiry before completion     -> expired
Explicit rejected record     -> rejected
```

`mob sign c-N` first shows and signs the prepare authorization. It then calls
`POST /v1/venue-bindings/prepare` with the persisted prepare idempotency key.
The returned requests become ordered `sign-text` or `sign-typed` cards. Their
submit marker only collects the exact signature into the ceremony.

After all accepted requests, the CLI shows and signs one read authorization,
submits the collected request signatures with the persisted `c-N:<uuid>` key,
and polls every five seconds for up to ten minutes. `bound`, `already_bound`,
`failed`, and `expired` are terminal venue results. Failures print the server
code and `retryable` value. A rejected middle request ends the signing session;
an accepted subset is submitted and the CLI names the venues left incomplete.

The browser ceremony lists every step and its status. It shows the current
purpose, exact message or typed data, and digest. Each request needs its own
Sign click. Reject ends the session. Owner checks run for each step. The page
switches to a pinned chain when needed, including 42161 for HL and 56 for
Aster; text requests need no chain.

`mob onboard --native` stages legal acceptance when needed, then the binding
ceremony. A fully successful ceremony stages `mob keys create` for the venues
that were just bound with the $5,000 cap. `mob bind --all` only performs the
ceremony.

## Dependencies and deliberate omissions

- W18 `@mstack/mobius-api` and W19 `@mstack/keys` are workspace dependencies.
  No third-party package or external runtime dependency was added.
- The native path does not call client-side HL funding or Lighter account
  discovery. The old per-venue repair path keeps those checks for W22.
- Tests and smokes use fake auth, funding, browser wallet, WalletConnect, and
  Strategy API services. No live key, venue, or binding request was used.
- A human must still use the real Mobius page, connect a real wallet, approve
  each real signature, and paste or import the resulting key.
- The production Strategy API 1.2 deployment and real-wallet validation remain
  external release work described in `docs/MOBIUS-ASKS.md`.
- No remotes changed and nothing was pushed.

## Rebase

W20 was rebased onto W21 commit `ad029d2` (`feat(trade): submit Proposals with
the API key`). The rebased tree keeps both feature sets:

- Config accepts and returns both `app_base` and `strategy_api_base`. Each key
  reports its own name in URL validation errors.
- Browser onboarding keeps public legal and readiness reads on `auth_base` and
  `api_base`. Stored-key verification and native ceremony prepare, submit, and
  read calls use `strategy_api_base`.
- The home screen keeps W21's warning for `policy auto`. Successful W20
  onboarding still follows the home screen with its `Ready · …` summary.
- The CLI parser and help include `onboard`, `bind --all`, `submit`, and both
  new config keys. Root and CLI package scripts include all three new smokes.
- `@mstack/proposals` exports the ceremony store while retaining W21's
  `api-submit` kind and durable `.submission-used` marker. Ceremony signing is
  narrowed to text or typed payloads, so W21's unsigned `none` payload cannot
  enter a ceremony record. The validator checks this rule after every read.
- The sign guard accepts `c-N` only for `mob sign`. W21's `mob submit` path
  still accepts only `p-N`, and `policy auto` still blocks wallet signing.

## W20.1

Two compiled-binary hand-run defects were fixed.

All onboarding legal and readiness reads now use `MobiusClient`. The client
adds `X-Mobius-Client: mstack/0.3.0`, `User-Agent: mstack/0.3.0`, JSON
acceptance, redirect refusal, timeout, pacing, response validation, and safe
errors. The aggregate `/api/binding/readiness` route accepts the current object
shape and the older array shape used by key-creation fixtures. W20 native legal
and readiness reads and the key-creation readiness check use the same route.

Ceremony records still store millisecond timestamps for local expiry. Every
wire payload now converts that value with `Math.floor(expiresAt / 1000)`. This
produces an integer Unix timestamp accepted by `preparePayload`,
`readPayload`, and the Strategy API with a real clock. `mob proposals` now
lists active ceremonies as well as `p-N` Proposals.
