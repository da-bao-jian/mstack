# W25 — best-practice alignment and plugin readiness

Built on `main` at version 0.4.0. The version and tag were not changed. No runtime dependency was added.

## Scope

Compare the stack against published guidance for agentic tool stacks and fix the gaps:
Anthropic (Building effective agents, Writing tools for agents, context engineering, Claude Code
best practices, Agent Skills, plugin/hook/MCP references), OpenAI (practical guide to building
agents, Agents SDK guardrails and approvals, function calling, Model Spec, Codex skills and
AGENTS.md), the MCP 2025-06-18 specification, OWASP LLM and Agentic Top 10, Simon Willison's
prompt-injection patterns, Google's secure-agents paper, 12-Factor Agents, agentskills.io, and
gstack 1.5.1.0 as the reference user-installed stack.

## Findings

Aligned without change: staged Proposals with one signing and one submission entrypoint, the
exact-id rule read from the latest human message, scoped key custody with stdin-only import,
read-only and staging-only MCP with explicit tool annotations, bounded tool output, namespaced
tools, fail-fast adapters, skill frontmatter and size limits, CLI stream and exit-code
discipline, no telemetry, pinned dependencies, deterministic skill generation with a CI drift
check, hourly update checks, `mob doctor`, and a ledgered uninstall.

Gaps fixed in this package:

- The root `.mcp.json` was also read as project configuration whenever the checkout was opened
  in Claude Code. `${CLAUDE_PLUGIN_ROOT}` is undefined there, so the server never started for a
  contributor. `${CLAUDE_PLUGIN_ROOT:-.}` was tested and rejected: the plugin loader does not
  treat that form as the plugin root, so the plugin broke outside the checkout instead. An
  inline `mcpServers` entry fixed the start-up; the follow-up question was whether the plugin
  should register a server at all. See the decision below.
- The Bash sign guard let a call through when the hook could not start, crashed, or timed out,
  because Claude Code treats those as non-blocking errors.
- The router had no route for install health, upgrade, or uninstall.
- The agent install doc did not offer the one-paragraph host instruction snippet that setup
  already prints, the way gstack's install prompt does.
- No runnable eval checked that a real session routes a request to the right skill.
- Stale text: README said the 0.4.0 tag was deferred; the CLI README hard-coded `mstack/0.2.0`
  in the client header; the 0.4.0 changelog section had a misplaced bullet; three documents
  described the MCP server through `.mcp.json`.

## Decision: CLI-first in Claude Code

The plugin registers no MCP server. Measured on this checkout:

- The ten `SKILL.md` files hold 43 `mob …` command references and no MCP tool reference. One
  reference document mentions MCP in a single sentence.
- All 18 MCP tools wrap CLI subcommands; none adds a capability the CLI lacks.
- `tools/list` plus the server instructions total about 3,500 tokens, loaded eagerly in every
  Claude Code session on a machine with the plugin, whether or not the user trades.
- The sign guard, exact-id check, and fail-closed setting sit on the Bash tool. One surface
  means one enforcement point.
- A server that fails to spawn is reported once at session start and is easy to miss; a CLI
  call fails in front of the user and can be retried in the same session.
- The Codex setup never registered an MCP server, so the CLI-only surface was already proven
  complete with the same skill templates.

`mob mcp` stays in the binary, tested and documented, for Cursor, Windsurf, Claude Desktop, and
any stdio client, and as the prototype of the P2 hosted MCP. Claude Code users opt in with
`claude mcp add --scope user mstack -- mob mcp`.

## Delivered

- `.claude-plugin/plugin.json` registers no MCP server and the root `.mcp.json` is removed.
  `claude mcp list` shows no mstack entry and no project-configuration warning inside or
  outside the checkout. The documented opt-in was verified in a throwaway `CLAUDE_CONFIG_DIR`:
  `claude mcp add` followed by `claude mcp list` reported `✔ Connected`.
- `hooks/hooks.json` sets `onFailure: "block"` and a 30-second timeout. On Claude Code 2.1.295
  or newer a guard failure blocks the call. SECURITY.md records the older-host behavior.
- `/mob` routes install health, upgrade, and uninstall to `mob doctor`, `mob upgrade` on request,
  and the per-host uninstall commands in `references/commands.md`.
- `docs/AGENT-INSTALL.md` gains an Integrate section: the agent shows the mstack paragraph and
  adds it to `CLAUDE.md` or `AGENTS.md` only when the user says yes. The doc stays under 150 lines.
- `packages/repo-hygiene.test.ts` pins one version across package, plugin, and marketplace
  manifests, the absence of `mcpServers`, a root `.mcp.json`, and a root `CLAUDE.md`, and the
  hook's `onFailure`.
- `scripts/eval-skills.ts` (`MOB_EVAL=1 bun run eval:skills`) runs six prompts through
  `claude -p --plugin-dir . --max-turns 1` with Bash denied and checks the Skill tool call. A
  first hop into `/mob` counts as correct routing because the router claims first-contact
  phrases by design. The script is skipped without `MOB_EVAL=1`.
- `CONTRIBUTING.md` explains running the plugin from a checkout through a directory marketplace.
- `CHANGELOG.md` has an Unreleased section for the next release.

Deliberate omissions, with reasons recorded in the report notes: no `disable-model-invocation`
on mutation skills (the hook, not skill invocation, is the gate); no
`anthropic/requiresUserInteraction` on `propose_*` (staging is not consent; per-call prompts
train confirmation fatigue); no MCP `outputSchema` yet; the hook stays in shell form because a
host that ignored exec-form `args` would run bare `mob` and exit 0; strict plugin validation
stays in the release checklist because CI runners lack Claude Code.

## Dependencies, questions and omissions

- Dependencies: none added.
- Specification question: `docs/PRD.md` (section 4 table, the distribution table, and the
  repository tree) still lists `.mcp.json` or an inline `mcpServers` entry as part of the Claude
  Code plugin. This package deviates deliberately and did not edit the PRD. The coordinator
  should amend the PRD or record the deviation.
- Not done here: pushing the `v0.4.0` tag, publishing a release, or changing repository
  visibility. Until a release exists, `install.sh`, the README paste prompt, and the GitHub
  marketplace path cannot work for anyone without a checkout. The manifest version must change
  (`bun scripts/release.ts 0.4.1 --prepare`) before plugin users receive this package.
- The human live checklist in `docs/READINESS.md` is unchanged.
