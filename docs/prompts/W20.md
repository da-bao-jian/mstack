## 1. `mob onboard` — browser path (default)
- Args: `[--owner 0x…] [--app-base URL] [--watch] [--native] [--venues …]`. Saves `owner` (asks on the TTY when absent; refuses without a TTY unless `--owner` is given), keeps `signer`/`policy` as they are (`policy` default `manual`), sets `app_base` (default `https://app.mob.exchange`, config key, validated like `api_base`).
- Opens `${app_base}/?nav=api` with the existing opener (`MOB_NO_OPEN`/`BROWSER` honored), at most once per hour per owner (stamp in `MOB_HOME`), and always prints the URL. No query parameters, no receiver, no localhost server: the user copies the key from the page and pastes it into the chat (agent path) or into `mob keys import` (human path). Print those two sentences verbatim under the checklist.
- Prints a checklist from public reads only: legal acceptance (`GET <auth_base>/legal/acceptance?wallet=`), each venue from `GET <api_base>/api/binding/readiness?ownerAddress=` (bound / needs repair / not bound, with the readiness issue text), and the key (none / stored `mobius_ab12…` / verified ok). On a TTY with `--watch` (default when a TTY is present) it redraws every 5 s until everything is green or 15 minutes pass; in an agent shell it prints once, exits 0, and ends with one `Next:` line (`Next: bind hl on the page`, `Next: paste the key in the chat`, `Next: mob keys import --stdin`, or `Ready`). Brand `style()` on a TTY, plain when piped. Idempotent: re-running skips what is done.
- When the key is stored, verify it through `@mstack/mobius-api` (`GET /v1/delta-neutral/tasks?limit=1`, 200) and finish with the home screen plus `Ready · <n> venues bound · key mobius_ab12… · cap $5,000` (cap from the key meta when known).
- Tests: fake auth and funding servers for the checklist (bound, repair, not bound, legal missing), the once-per-hour opener stamp, `--watch` through a PTY with a fake clock, the agent path (`mob keys import --stdin` from W19.1 then `mob onboard` → Ready), `MOB_NO_OPEN`.

## 2. `mob onboard --native` and `mob bind --all`
- For `signer` = `keystore` or `walletconnect` (and `browser`, which gets the page from section 3). Steps: legal acceptance Proposal if not accepted (existing code), then one **ceremony** `c-1` for the chosen venues (`--venues hl,lighter` default: all four minus already-bound), then `mob keys create` staged with the venues just bound.
- Ceremony = a new record type in `@mstack/proposals` (`ceremonies/c-N.json`, same permissions and locking as Proposals) holding: owner, venues, `bindingId`, `expiresAt`, the prepare Proposal, the per-request Proposals (one per `signRequest`, each a normal `sign-text`/`sign-typed` Proposal whose `submit` is "collect into ceremony", not an HTTP route), the collected signatures, the submit Idempotency-Key (`c-N:<uuid>`), the latest read result. `mob sign c-1` signs the pending steps **in order in one signer session** (keystore: one passphrase; WalletConnect: one pairing, one approval per step; browser: the multi-request page of section 3), then prepares/submits/polls as the ceremony state requires. Every step is still shown as its own card before its signature; nothing is signed without the user naming `c-1`, and the sign-guard treats `c-N` ids like `p-N`.
- Protocol through `@mstack/mobius-api`: `preparePayload` + `bindingMessage("prepare")` signature → `POST /v1/venue-bindings/prepare`; classify each `signRequest` with `classifySignRequest` and sign exactly the returned payload; `POST …/submit` with the ceremony's Idempotency-Key (a subset is allowed when a step was rejected; say which venue stays incomplete); then `readPayload` + `bindingMessage("read")` signature (reused within its window) for `GET …/{bindingId}` every 5 s until every venue is `bound`/`already_bound`/`failed`/`expired` (10-minute budget; `failed` prints `code` and `retryable`; `rebind_required` explains and offers `--rebind`). HL account precheck and Lighter account discovery happen server-side now; drop the client-side `funded()` and account-index lookups for this path but keep them for the old per-step `mob bind <venue>` until W22 removes it.
- `mob bind --all` is the same ceremony without the legal and key steps. The old `mob bind <venue>` stays as the repair path.

## 3. Multi-request sign page
- The browser bridge serves a session for one ceremony: one tab, one wallet connection, the steps listed with their status, the current step's card (purpose, exact message or typed data, digest), **Sign** per step, no auto-advance without a click, Reject ends the session. The page keeps W15's brand, CSP nonce, no external resources, expected-owner and chain checks per step (chain switch between steps when the pinned chain changes: 42161 for HL, 56 for Aster, none for text).
- `mob sign p-N` keeps the single-Proposal page unchanged.
- Tests: the fake browser wallet drives a 5-step ceremony in one session; a rejected middle step leaves later steps unsigned; a chain switch between steps; the digest shown equals the terminal's.
