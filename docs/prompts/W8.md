## W8 — browser bridge and WalletConnect signers (docs/BUILD-PLAN.md W8), one commit per backend

### W8a `browser` — commit `feat(signers): browser bridge`
1. In-process, one-shot: `mob sign <id>` (with `signer=browser` or `--with browser`) starts an HTTP server bound to 127.0.0.1 on a random port inside the CLI process, serves one Proposal, and closes after one accepted signature, a rejection, or the Proposal's expiry. No persistent daemon, no token file on disk. Print the URL, then open it with `open` (macOS), `xdg-open` (Linux) or `start` (Windows) through an injectable `openUrl`.
2. The page is one HTML file bundled into the binary (Bun text import). No external resources; a strict CSP header from the server (`default-src 'none'; script-src 'nonce-…'; style-src 'nonce-…'; connect-src 'self'`). It discovers wallets with EIP-6963 (`eip6963:requestProvider` / `announceProvider`), falls back to `window.ethereum`, calls `eth_requestAccounts`, and shows: purpose, the expected owner, the selected account (red mismatch and a disabled button when they differ), the exact message in a `<pre>` (or the typed-data JSON), the digest with the sentence "compare this digest with your terminal", and a countdown to expiry. For `sign-text` it calls `personal_sign` with the hex-encoded UTF-8 message and the address, in that parameter order. For `sign-typed` it calls `eth_signTypedData_v4` with the address and the JSON string. When the Proposal pins a chain (typed data with a `chainId` in its domain), it calls `wallet_switchEthereumChain` first and shows the error if the wallet refuses; it never calls `wallet_addEthereumChain`.
3. Server API: `GET /sign/<id>?t=<token>` serves the page; `GET /api/proposal?t=` returns the Proposal view; `POST /api/signature?t=` takes `{ address, signature }`. The token is random, per run, single-use for the POST. The server checks: token present and equal; `Origin` equals its own origin on the POST; the recovered address equals the Proposal owner (viem `recoverMessageAddress` / `recoverTypedDataAddress`); not expired. A rejected POST answers 4xx with a short reason and the server keeps waiting until expiry; an accepted one returns 200 and resolves the pending `signMessage` / `signTypedData` call.
4. `Signer` gains an optional `chainId(): Promise<number>` reported by the page (the wallet's current chain), which W9 needs for Hyperliquid typed data.
5. Config `signer=browser` needs no secret. `mob sign` with `browser` works from an agent's shell: the human clicks in the wallet.
6. Tests: a scripted fake wallet (a viem account) drives the server through its HTTP API with an injected `openUrl` that captures the URL: happy path for text and typed data; wrong signer rejected; missing or wrong token rejected; second POST rejected; wrong `Origin` rejected; expiry closes the server and the sign call fails with the expiry message; the served HTML contains no `http(s)://` references and carries the CSP. Add a `scripts/smoke-browser.ts` that runs the fake-server Proposal flow with the fake wallet and prints the transcript (no real browser in CI).
